## Method and dataset

The public sample has 32 cases; the evaluation input has 518. The program uses identity snapshots and history, 4,011 activity rows, 15 policy rules, and 94 manifested evidence files. Each sample prediction is generated by the same `audit` function as the final CSV. Exact step precision and recall compare all step fields except `step_no` as a multiset; position-aligned metrics compare rows at the same array index.

## Failures and improvements

The first parser missed handover rows, trace-linked log events, SQL JSON payloads, PDF attachments, and screenshots. The implementation now parses those formats, caches OCR text from participant-facing images, recovers historical identifiers, and filters evidence by audit time. Public-sample status accuracy improved to 32/32. Exact step arrays still differ in 17 cases, chiefly because compliant absent, anonymized, and retained records can lack an explicit subject identifier in the parsed evidence. Additionally, 4 full-run COMPLETE rows have no verification step; they cannot be treated as proven complete under the challenge contract. These are unresolved scoring risks. The engine does not substitute workflow claims for proof.

Strict validation: **FAIL**, 4 mandatory errors. The machine-readable details are in `evaluation/validation_report.json`. CSV shape, ordering, operation/state pairs, and cited evidence timestamps passed. Structural validity does not establish substantive correctness.

## Reproduction

Run `python3 code/main.py`, `python3 -m unittest discover -s code/tests`, `python3 code/evaluation/main.py`, then `python3 code/evaluation/validate.py` from the repository root. The last command intentionally returns a nonzero exit code while mandatory validation errors remain.
